# 面向 L4 量产的数据与可观测性 Harness 方案

日期：`2026-09-12`。
授权范围：`design_only`。本次只出方案、记录文档，不修改代码、不部署、不进行车辆测试。
方案状态：`proposed/recorded`；实现状态：`not_started`；运行验证状态：`not_run`。

数据库和行业公开资料见
[专题 23：车端数据平台选型](23-vehicle-data-platform-selection-20260912.md)。
代码级基线仅保存在 Git 忽略的本地保密附录，不复制到本方案。

## 1. 目标对齐

总体目标是 L4 量产；本专题承担其中的**数据与可观测性子系统**。
其交付目标不是安装若干数据库，而是：

1. 在批准的资源预算下持续产生可信的业务、系统和原始事件证据。
2. 关键数据具有明确的完整性、时间质量、耐久确认和恢复边界。
3. 故障后能复现、定位、回归验证，支撑版本发布和车队质量管理。
4. 新增诊断、查询、采集或上传失败时，不破坏既有控制与安全隔离。
5. 每项“已完成”都有版本、输入、执行结果和可复核证据。

这些目标不能替代整车 ODD 定义、感知/决策能力、故障降级、安全分析、
场地/道路验证和适用的准入评审。数据 Harness 全部通过不等于整车达到 L4。

如果某类记录能力属于整车安全要求，应由安全方案定义其失效响应；
不是简单规定“所有记录故障都不处理”，也不是让 Collector 自主触发 MRC。

## 2. Harness 原则

本方案将 Harness 定义为：围绕实际系统建立可重复的输入、受控执行、观测、
确定性验收、证据留存和发布门禁，而不是只做一个 AI 自动操作入口。

| 原则 | 本方案中的具体要求 |
|---|---|
| 目标锁定 | 每个任务关联需求 ID；不能以新增组件数量代替目标达成 |
| 范围约束 | 数据/观测变更不夹带控制策略、MRC 或驾驶算法修改 |
| 先验收后实现 | 先定义失败场景、预期结果和预算，后续获准后才实现 |
| 可复现 | 固定代码、构建、配置、输入数据、Schema、环境和随机种子 |
| 独立裁决 | 执行者产出证据，验证器按既定规则判定，不采信“自述已完成” |
| 有界运行 | 每个测试有时间、CPU、内存、磁盘、网络和重试上限 |
| 故障隔离 | 测试、观测和查询不能成为实时控制的同步依赖 |
| 明确未知 | 缺环境/证据为 NOT_RUN 或 BLOCKED，不算 PASS |
| 证据驱动迭代 | 新问题形成固定场景和回归检查，而不只追加说明文字 |
| 人工发布门禁 | 模型可以辅助分析，不自动批准车辆发布或安全动作 |

## 3. 需求到证据的映射

| 需求 ID | 目标 | 所需证据 | 不接受的替代物 |
|---|---|---|---|
| DATA-001 | 观测故障与既有控制隔离 | Agent 开/关、失败/重启时的真实 deadline 和行为对照 | “使用了异步线程” |
| DATA-002 | 关键事件持久确认明确 | 封口、校验、同步、状态提交和获准掉电恢复报告 | “存在 WAL/SQLite” |
| DATA-003 | 每次数据缺失可解释 | expected/written/dropped、序号、丢弃原因与完整性标记 | “生成了一个 MCAP 文件” |
| DATA-004 | 时间与因果不被混淆 | source/receive/monotonic、时钟域、同步状态和关联方法 | 用跨设备墙钟直接相减 |
| DATA-005 | 上传可重试且不重复生效 | 重复请求、分片重试、云端校验和任务幂等报告 | “HTTP 返回成功” |
| DATA-006 | 资源受控 | 峰值 RSS、共享内存、写放大、功耗、超限行为 | 供应商其他硬件的性能数字 |
| DATA-007 | 版本可升级与回放 | 旧文件读回、Schema 兼容、升级中断和回滚报告 | “新版本编译通过” |
| DATA-008 | 采集边界符合保密要求 | 字段白名单、出口限制、鉴权、访问/删除审计 | 只给目录加 Git 忽略 |
| DATA-009 | 可完成 5W 闭环 | 同事件的车辆/版本、时间、场景、阶段与原始证据 | 不同系统中各有一张看板 |

## 4. 运行系统与 Harness 分开

建议运行架构：

```text
既有控制/健康/安全路径 -> 保持独立

业务摘要 + 基础指标 + 可选 eBPF
  -> 有界异步观测通道 -> OTel -> 云端观测后端

原始事件窗口 -> MCAP/媒体封口 -> 持久文件 + 事务状态
  -> 受控上传 -> 对象存储 -> 解码/Parquet
```

建议验证架构：

```text
需求与预算
  -> 获准场景集
  -> 隔离环境执行或离线回放
  -> 只读证据采集
  -> 确定性检查 + 基线比较
  -> PASS / FAIL / BLOCKED / NOT_RUN
  -> 证据包
  -> 人工评审
  -> 下一阶段准入
```

单元/合成场景证明局部性质；不能冒充真实节点集成。
离线回放证明固定输入下的行为；不能证明物理传感器或执行器响应。
SIGKILL 测试证明进程恢复；不能替代掉电、介质和整机重启测试。

## 5. 数据库在这个目标下的取舍

| 组件 | 建议位置 | 进入下一阶段的理由 |
|---|---|---|
| SQLite | 本地事件/上传/清单事务状态 | 现有队列确实需要原子状态转换、租约和启动对账 |
| MCAP | 原始消息和事件窗口 | 保留可回放记录，先解决类型、压缩、封口和完整性 |
| Parquet | 解码后的批量分析数据 | 支持跨事件分析并记录转换血缘 |
| DuckDB | 工作站/云端离线分析；车端按需隔离查询 | 用真实查询验证是否需要更复杂的在线库 |
| GreptimeDB 云端 | 在线时序/日志查询候选 | 当前后端的查询、成本或运维缺口经过证明 |
| GreptimeDB Edge | 有持续车内写查需求的设备 | 同等负载下通过资源、耐久、授权和迁移验收 |
| OTel | 语义、Trace Context 与异步传输 | 接通已存在的高价值事件，不全量包装原始数据 |
| eBPF | 经目标内核验收的系统事实源 | 能解释应用埋点无法解释的问题 |
| collectd | 现有部署或专用插件兼容层 | 不与其他采集器重复扫描同类主机指标 |

首期不要求 SQLite、DuckDB、Edge 同时常驻。
推荐以“MCAP + 可靠状态 + OTel + 对象存储”为运行主线，
“Parquet + DuckDB”为离线验证主线。
GreptimeDB 云端和 Edge 分开评估，不因云端候选通过就直接批准 Edge 上车。

## 6. 场景矩阵

以下是待实现的验收设计，不是已执行测试。

| 场景 | 预期检查 | 允许的环境 |
|---|---|---|
| 正常事件 | ID 一致、窗口完整、类型可读、云端对象可校验 | 合成/离线/集成 |
| 重复触发/重复上传 | 事件语义明确，不重复生效 | 合成/隔离集成 |
| 网络断开与恢复 | 队列有界、退避、优先级、续传、最终对账 | 隔离网络/台架 |
| 上传成功但确认丢失 | 幂等重试，不能提前删除本地证据 | 隔离集成 |
| 文件写入中进程退出 | 临时文件不冒充完整文件，恢复报告明确 | 临时目录/台架 |
| 封口与账本提交之间退出 | 孤儿文件和悬空任务可对账 | 临时目录/台架 |
| 断电 | 持久确认之前/之后的真实 RPO 和恢复结果 | 获准台架 |
| 磁盘满/只读/IO 错误 | 分级配额、显式失败、控制隔离 | 故障盘/获准台架 |
| 大消息与事件风暴 | byte/message 上限，压缩加密同时驻留峰值 | 回放/台架 |
| 时钟跳变/未同步 | 时间质量被标记，不伪造端到端耗时 | 合成/回放 |
| 类型/软件版本升级 | 旧数据可解码，派生表可追溯 | 离线/集成 |
| Agent 崩溃或查询超时 | 控制、录制等独立路径不被新依赖阻塞 | 回放/获准台架 |
| 观测开销对照 | 各阶段 deadline、FPS、CPU/RSS/IO 差异 | 同负载台架/获准实车 |
| 未授权字段/查询/出口 | 拒绝且有审计，不泄露正文 | 合成/隔离安全测试 |

默认使用合成或获准脱敏样本；真实代码、日志、MCAP 和内部地址不进入公开检索。

## 7. 证据包设计

未来实现应产生以下逻辑工件；本次不创建其程序或运行结果：

```text
requirements + acceptance_profile
scenario_manifest + input_hashes
build/config/schema/environment_manifest
execution_summary + resource_measurements
check_results + baseline_comparison
artifact_index + checksums
review_decision + unresolved_risks
```

每条检查至少记录：

```text
requirement_id, scenario_id, build_id, config_revision
execution_mode, started_at, duration, exit_reason
expected, observed, threshold_revision
verdict, evidence_refs, known_limitations
```

状态约束：

- `PASS`：检查实际执行，证据完整，达到已批准标准。
- `FAIL`：实际执行，但至少一项标准不满足。
- `BLOCKED`：依赖/环境不具备，记录原因，不等价于系统故障。
- `NOT_RUN`：未执行；不能从文档推定通过。
- “记录了计划”“进程启动成功”“单元测试通过”不能提升为整车量产通过。

## 8. 分阶段准入

| 门禁 | 工作内容 | 放行条件 |
|---|---|---|
| G0 目标与边界 | ODD/车型、数据等级、资源与耐久需求、保密边界 | 需求、责任人和验收口径明确 |
| G1 离线合同 | 合成事件、状态机、类型/时间、幂等与数据质量 | 确定性检查和失败路径可复现 |
| G2 原系统集成 | 既有录制/上传链路，加最小观测桥接 | 原始数据可回放，事件可完成 5W 对账 |
| G3 故障与耐久 | 重启、断网、磁盘故障、获准断电 | RPO/RTO、丢失与恢复符合分级要求 |
| G4 资源与选型 | OTel/eBPF 开销；SQLite/DuckDB/Edge 公平对照 | 不超实时预算；数据库需求和收益成立 |
| G5 小范围车辆 | 有授权的目标车型长时间测试 | 配置、证据、升级回滚和已知风险被评审 |
| G6 量产运维 | 分批发布、版本治理、车队质量和回归闭环 | 与整车安全/发布体系共同批准 |

没有经过整车安全与量产发布门禁，不得把 G1-G4 的结果命名为“L4 已量产”。
本轮所有门禁为 `NOT_RUN`；现有设计和代码审查只作为准备材料。

## 9. 资源与数据预算

必须由目标硬件、业务 deadline 和数据等级导出，不预先承诺通用 CPU 百分比。

至少约定：

- 每类组件的 CPU 核秒、峰值 RSS、共享内存、临时盘和闪存写入预算。
- 关键路径 P99/P99.9、deadline miss、掉帧和抖动上限。
- 每级数据保留时长、关键事件预留字节、最长获准断网时长。
- 持久确认点、可接受 RPO/RTO、上传带宽和重试上限。
- 车内 SQL 的查询范围、并发、超时、运行窗口和 spill 配额。
- 每车和云端的授权、带宽、对象/索引存储、计算与维护成本。

数据库比较使用同一数据、采样、压缩、耐久和查询条件。
预算未确定属于门禁未通过，不通过降低耐久设置来“优化”测试数字。

## 10. 首批工作包设计

未来取得实现授权后，建议按以下范围拆分，分别评审和回滚：

1. **采集器基线**：修正已有采样和数据质量问题，不改安全策略。
2. **事件完整性**：字节预算、封口、类型/时间质量、文件与任务对账。
3. **观测桥接**：统一计数 owner、业务事件 ID、OTel 白名单和有界出口。
4. **离线验证**：受控解码 Parquet、DuckDB 查询模板和回归证据。
5. **系统归因**：按目标内核逐步增加 eBPF，不先开启全量 profiling。
6. **数据库 POC**：云端 GreptimeDB 与车端 Edge 各自评估，不同步强推。

不在首批范围内：驾驶算法重构、MRC 状态机修改、远程控制协议变更、
任意 SQL/Shell/BPF 远程执行、量产车自动部署、全量原始数据上传和现网数据库迁移。

## 11. 当前需要定版的方案输入

优先确定首个目标平台、真实启动入口、需保障的数据等级、离线留存时长、
实时资源预算以及是否确有“行驶中车内在线 SQL”需求。

在这些输入明确前，可继续设计合成/离线验收，不应承诺某数据库已经最优。
默认方案仍是：复用现有录制与安全链路，补足可靠状态与观测证据；
DuckDB 先离线，GreptimeDB 云端/Edge 以实测门禁决定是否引入。
